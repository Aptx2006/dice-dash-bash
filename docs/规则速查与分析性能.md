# 规则速查与分析性能

日期：2026-10-28。继续开发游戏；实验6报告保留原模板。

## 对局内查规则

对局工具栏增加“规则速查”。原生dialog隔离背景点击并管理焦点，可点击关闭或按Esc返回对局。

- “基础与手牌”说明投骰、使用手牌、结束两个阶段及胜负方式。道具选择仅来自自己的手牌，重复道具按类型合并；卡牌描述读取`TOOLS`现有定义和手牌参数。未持有移动牌时使用一般说明，避免未投骰显示“0格”。
- 补充滑行、制动、冲刺前提、瞬移合法目标及牵引操作顺序。具体目标仍以当前规则引擎的高亮为准。
- “向教练了解…”仅填入问题，点击询问才请求模型；复用已有RAG接口、取消、超时、来源检查与错误提示。关闭手册卸载问答组件并取消等待。没有把规则问答包装成当前局面分析。
- 无需模型的速查可离线阅读。查询请求只含问题文字与`mode: rag`，不附带玩家、房间、手牌或完整棋盘。自由输入的问题仍由玩家决定内容。
- 查阅期间对局、机器人和计时继续；界面明确提示。不会因为一个玩家查规则而暂停整个房间。
- 首页和对局复用问答组件，使用Vue生成的唯一label/textarea标识。窄屏工具栏保持单行，短横屏为左侧回合提示预留空间。

主要实现：[MatchRules.vue](../src/components/MatchRules.vue)、[RulesCoach.vue](../src/components/RulesCoach.vue)。

## 同一快照内复用推演

原实现每次`list_actions`先枚举全部行动，再为每个行动调用`inspectTacticalAction`，后者又重新枚举全部行动；翻页和最终检查重复上述工作，瞬移候选较多时尤其明显。

新增`createTacticalAnalysis`：创建独立深拷贝，一次展开合法候选，按编号延迟推演并缓存结果，到终点的起始距离只计算一次。每次读取都返回副本，不能通过改写工具结果污染后续检查。Harness每次运行有独立context，弱引用缓存随context释放；玩家助手和云端对手不共享一次分析，也不跨房间、玩家或回合缓存。规则接管策略同样用一次分析评价全部候选。

保留`inspectTacticalAction`独立调用接口及真实引擎推演。缓存只加速只读分析，不缓存真实执行权限；执行仍检查局面指纹、当前活动玩家、阶段和合法行动。推演不会消费真实随机源、奖励、日志/特效/手牌编号。

实现：[tactical.ts](../src/game/tactical.ts)、[tools.ts](../server/agent/tools.ts)、[opponentController.ts](../src/agent/opponentController.ts)。

## 可复现基准

```powershell
npm run bench:tactics
npm run bench:rooms
```

Node 22.23.2，本机Windows。耗时会随设备负载波动；不把单次结果作为稳定性能保证。

`bench:tactics`在三张地图构造8人、罗素持6点移动/瞬移/瞬步/冲刺牌的合成局面。每轮连续查询3次全部候选，预热4轮后记录10轮；先逐项验证新旧全部推演结果一致并检查原状态未改变。

| 地图 | 候选数 | 原实现中位数 | 快照分析中位数 | 原实现P95 | 快照分析P95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| race1 | 95 | 91.65ms | 8.73ms | 95.27ms | 8.88ms |
| race2 | 105 | 102.10ms | 9.51ms | 102.90ms | 9.59ms |
| race3 | 120 | 131.39ms | 12.39ms | 134.35ms | 13.46ms |

这是候选计算的约10.5～10.7倍加速，不能等同于云端模型响应加速。

`bench:rooms`另建随机本机端口及临时SQLite，使用实际HTTP、SSE和WAL/FULL事务，3个房间各8名真人连接，共24个SSE客户端。三房并行，每人执行投骰、结束行动、结束回合，共72条命令。逐帧检查其他玩家手牌为空，测量请求发出到同房所有客户端收到对应版本的时间；不含前置读取版本的GET、渲染或动画耗时。测试禁用演出保留时间和回合计时，没有AI/模型请求。

首次结果：接收1176帧；中位17.47ms，P95 27.53ms，最大30.01ms；私有手牌检查通过。临时库在关闭服务后，仅清理经过路径校验的本次临时目录，不触碰玩家数据库。

该基准是同进程客户端的本机回环测量，不代表校园网、跨设备延迟、互联网部署或真实手机触控验收。课程中“校园网95%同步500ms”目标尚不能据此记为通过。
