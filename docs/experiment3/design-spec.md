本文件保存报告第3、4部分的设计内容。插图由同目录脚本在本地生成，图号与报告一致。


项目名称：**《当骰一棒》（Dice, Dash & Bash）——类桌游多人回合制竞速游戏**。记录日期：2026年9月28日。本次以实验2的用户故事、验收示例和现有本地人机原型为输入，形成后续迭代的设计基线。现有项目已使用 Vue 3、TypeScript、Vite、Three.js；本文的统一命令入口、服务端存储、模型 Agent、RAG 和 Harness 均为待实现设计，不作为已完成功能。

### 3.1 需求输入与设计范围（对应2.1）

选定的核心流程为：**输入昵称 → 创建本地房间 → 配置智能体 → 开始游戏 → 真人与智能体轮流行动 → 首位玩家到达终点 → 查看结算**。教学关作为同一流程的简化入口，默认配置一名教学智能体。真实跨设备联机保留接口边界，本次不设计账号、支付、社交、排行榜和地图编辑器。

### 3.2 技术选型与架构决策（对应2.2）

选型以已有代码和单人课程项目的交付成本为主要依据。当前依赖声明为 Vue 3.5、TypeScript 5.9、Vite 7.1、Three.js 0.180；继续沿用现有版本约束，不为设计报告升级运行依赖。

| 决策 | 候选方案 | 选择、理由及不足 |
| --- | --- | --- |
| ADR-01：页面与棋盘 | Vue + Three.js；改写为 React；Unity 客户端 | 保留 Vue + TypeScript + Three.js，已有页面、规则和相机代码可复用；固定视角与简洁地块满足2.5D表现。代价是需控制渲染体积，规则代码不能依赖 Three.js 对象 |
| ADR-02：体系结构 | 页面中直接调用全部逻辑；分层模块化单体；微服务 | 选择分层模块化单体。界面经 GameGateway 调用应用服务，规则集中校验；本地和未来远端网关共用命令类型。需要逐步从组件提取调度逻辑，但一人维护成本较低 |
| ADR-03：服务端语言 | Node.js + TypeScript；Python 服务 | 规划 Node.js + TypeScript，自有服务端承载权威状态和模型密钥，复用规则类型；Python 保留给离线分析。代价是同步重计算会影响请求处理，需限制模拟数量与单局工作量 |
| ADR-04：保存方式 | 全部 localStorage；SQLite；独立数据库服务 | 昵称与动画倍速保留在 localStorage；当前局面留内存。服务端阶段以 SQLite 保存快照、事件、命令回执和脱敏轨迹，规则保存为版本化文件。SQLite易于单机部署，但不适合高并发多写入节点，本学期不设计分布式数据库 |
| ADR-05：AI运行方式 | 直接在页面调用模型；后端轻量Harness；引入大型多智能体框架 | 规划后端轻量 TypeScript Harness，包含工具白名单、总预算、校验、降级和轨迹；模型适配层首选接入已有使用经验的 DeepSeek 云端API。没有指定课程框架，先完成单一对手决策闭环；工具循环与评估需自行实现 |

Vue对TypeScript的支持和独立类型检查方式参考[Vue官方文档](https://vuejs.org/guide/typescript/overview.html)。SQLite的适用范围与并发写入限制参考[SQLite官方说明](https://www.sqlite.org/whentouse.html)。这些资料用于解释选型，具体可用性仍由项目测试验证。

**关键依赖替代方案：** 模型服务不可用、限流或响应超时时，不等待人工更换密钥，立即采用规则策略继续对局；规则教练退化为展示已确认规则条目。模型接口预留智谱或百炼适配器，切换仅修改服务端配置，候选模型仍需验证结构化响应。SQLite写入失败时事务回滚，不广播成功状态；本地练习模式可独立运行，但不声称它具备服务端恢复能力。

| 模块 | 职责与依赖 |
| --- | --- |
| M1 界面与演出 | 首页、配置、对局、结果、相机和事件动画；调用M2，显示裁剪后的状态，不能自行改写规则资源 |
| M2 应用服务 | 管理本局配置、会话、调度与命令回执；调用M3/M4/M7，统一返回快照、事件或错误 |
| M3 规则引擎 | 枚举合法行动、验证阶段/目标、计算效果及终点判定；只依赖数据类型和注入的随机源，不依赖UI或模型 |
| M4 Agent Harness | 构造可见上下文，按预算调用M5/M6，校验输出并生成建议；失败时运行规则策略，轨迹交M7；实际动作仍交M2/M3执行 |
| M5 规则检索 | 读取经确认且与对局版本一致的规则；提供规则查询。实时局面和合法行动由M3提供，不能由知识库猜测 |
| M6 模型适配 | 封装云端请求、响应解析、取消和错误码；密钥只在服务端读取 |
| M7 存储与轨迹 | 保存快照、事件、幂等回执、脱敏轨迹；保存失败向M2返回明确错误，不产生部分成功 |

Eval Harness是开发侧验收工具，使用固定局面、规则问句和故障注入调用M3—M5，记录合法率、延迟、降级和引用支持情况。它不参与每次玩家操作，也不代替实际测试结果。

| 参与方 | 核心职责 | 禁止或约束 | 检查责任 |
| --- | --- | --- | --- |
| 用户 | 配置对局、选择动作、确认目标、阅读回答 | 不能在非本人回合修改状态 | 确认的是操作意图；合法性由程序检查 |
| 普通程序 | 骰值、规则、状态、排名、重试与降级 | 不信任前端参数和模型输出 | M2验证身份与请求；M3复验合法性并提交 |
| 模型 | 从合法候选中建议动作，生成简短依据或规则回答 | 不直接写状态、不生成可执行脚本、不读取隐藏手牌 | M4检查结构与预算；M3检查动作；M5/M4检查引用来源 |
| 工具 | get_rule、list_legal_actions、simulate_action等只读能力 | 白名单、最多2轮工具调用；模拟用状态副本与独立随机源 | M4限制参数和次数；M3保证模拟不消耗真实资源 |

模型在存在有意义的多选动作时介入；强制投骰等唯一选项由程序处理。每个AI回合至多进行一次模型决策，其余行动可由规则策略接续。初始总预算为5秒，包含检索和工具调用；超时后2秒内给出降级动作。这些时间是待测验收目标，动画播放不计入模型耗时。

### 3.4 数据、接口与核心流程设计（对应2.4）

**图3 核心数据模型。** 沿用现有GameState、PlayerState和ToolInstance概念，增加对局标识、状态版本、规则版本、有序事件和执行轨迹。一局包含2—8名玩家；当前本地配置为1名真人加1—7名智能体。每局固定一个已确认规则版本，规则包包含多个规则条目；普通行动事件可不关联模型轨迹。

图源：图3 核心数据模型，见[绘图生成脚本](generate_figures.py)。

| 数据与保存位置 | 关键字段、约束与敏感性 |
| --- | --- |
| GameConfig / GameState；本地内存，服务端阶段存SQLite快照 | mapId必须存在；玩家数量2—8；坐标合法；phase与finished一致。stateVersion从0开始，成功命令仅增加一次；rulesetVersion在局内固定 |
| PlayerState / ToolInstance；快照内嵌 | playerId局内唯一；昵称去空白后1—12字；牌uid在局内唯一并归属于持有人；隐藏手牌不包含在他人的可见快照和模型输入中 |
| ActionEvent；服务端SQLite | (matchId, seq)联合唯一，按seq播放；actorId引用局内玩家；一个命令可产生多条事件。公开事件不包含未公开手牌 |
| CommandReceipt；服务端SQLite | (matchId, requestId)联合唯一，保存请求摘要和原响应；同ID同内容重试返回原响应，同ID不同内容拒绝；不是把每条事件的requestId设为唯一 |
| RuleSet / RuleEntry；项目版本化文件 | version与hash标识规则包；(version, ruleId)唯一；只索引confirmed条目；来源必须能回溯到当前有效规则 |
| AgentTrace；服务端SQLite | traceId、状态/规则版本、actionId、sourceIds、耗时、提供方标识和降级原因；不保存密钥、隐藏推理过程或无必要的用户原始输入 |
| 用户偏好；浏览器localStorage | 仅昵称、倍速等低敏偏好；不保存API密钥。API密钥放服务端环境变量，会话凭据不写入报告或轨迹 |

未来服务端提交时，在同一事务中保存新快照、事件和命令回执；提交失败保持旧版本。先按会话和请求摘要检查已有回执，再检查expectedVersion，保证成功请求重发时不会被误判为新的过期操作。单局命令串行处理，避免两个请求同时消耗一张牌。持久化完成后广播裁剪快照；本次未将崩溃重连作为已实现功能。

以下是拟新增的模块接口契约，I1—I6均通过GameGateway或服务端内部服务暴露；不是现有HTTP接口清单。远端实现可映射为HTTP命令和状态订阅，首次实现先验证本地网关与相同类型契约。

| 接口 / 提供者 → 调用者 | 输入与用途 | 正常输出 | 失败情况 |
| --- | --- | --- | --- |
| I1 createMatch；M2 → M1 | requestId、mode、nickname、mapId、aiCount；教学模式固定1名AI | matchId、初始可见快照、version | INVALID_INPUT、INVALID_MAP、INVALID_PLAYER_COUNT；保留配置 |
| I2 getLegalActions；M3经M2 → M1/M4 | matchId、当前会话/内部AI身份、stateVersion | 带版本的actionId列表及目标/效果预览 | NOT_YOUR_TURN、STALE_STATE、MATCH_FINISHED |
| I3 submitCommand；M2/M3 → M1/M4 | requestId、expectedVersion、actionId、confirmed；身份从会话获得 | 新version、可见快照、events | INVALID_TARGET、CONFIRM_REQUIRED、STALE_STATE、REQUEST_ID_CONFLICT、MATCH_FINISHED；状态不变 |
| I4 decideAction；M4 → M2 | 可见局面、合法行动、规则版本、总预算 | actionId、简短理由、sourceIds、fallbackReason? | 超时/不可解析/非法输出则规则降级；无合法动作由引擎判断结束阶段 |
| I5 getResult；M2/M3 → M1 | matchId与读取权限 | 胜者、排序、未完赛距离、回合摘要 | MATCH_NOT_FINISHED、NOT_FOUND；不提前伪造排名 |
| I6 askRule；M4/M5 → M1 | 1—200字问题、matchId、rulesetVersion | answer、sources[{ruleId,title,version}]，或明确无依据 | 无依据返回NO_EVIDENCE；服务错误返回UNAVAILABLE并展示规则入口 |

**正常调用示例：** 给定真人p1的回合、stateVersion=12，I2已经返回绑定“使用uid=17的拳击牌、目标p2”的候选actionId=`a12-punch-p2`，玩家阅读预览并确认后提交：

```json
{
  "matchId": "m-demo",
  "requestId": "req-001",
  "expectedVersion": 12,
  "actionId": "a12-punch-p2",
  "confirmed": true
}
```

成功响应的摘要为`{"ok":true,"version":13,"eventSeq":[31,32]}`，同时返回对该玩家可见的新快照与两条事件。道具扣除一次；原请求再次提交，返回相同回执，不重复扣牌。actionId只在对应局面版本内有效，参数由服务端候选映射取得，客户端不能替换目标。

**错误调用示例：** 在同一初始局面，若`confirmed=false`且该道具需要人工确认，则返回：

```json
{
  "ok": false,
  "code": "CONFIRM_REQUIRED",
  "message": "请确认对小棒使用拳击",
  "currentVersion": 12,
  "events": []
}
```

此时位置、手牌和版本均不改变。确认后使用新的requestId重新提交；若局面已变化，则返回STALE_STATE并刷新候选动作。以上是接口样例，不是实际运行日志。

**图4 核心行动流程。** 真人选择、预览与确认，以及智能体模型建议/规则降级，最终都进入同一权威校验入口。失败返回原因和最新版本；成功提交后才播放有序事件。动画结束后继续行动或进入结算，迟到的模型响应和结束后的动作被丢弃。

图源：图4 核心行动流程，见[绘图生成脚本](generate_figures.py)。

### 3.5 界面原型与交互设计（对应2.5）

本次采用**矢量线框图与可点击HTML原型**，按课程允许的页面草图方式完成设计。四张关键界面是面向下一轮迭代的设计稿，以现有原型的操作问题为输入；不是游戏实测截图，也不以已有前端页面替代原型。每张保留可编辑SVG和高清PNG，交互稿用于演示导航、校验提示、确认和异常情境。

## 实验小结


本次实验把《当骰一棒》从需求描述推进到能够指导下一轮开发的设计基线，完成了需求追踪、五项架构决策、系统上下文、模块结构、数据模型、六个接口契约、行动流程、页面导航和四张关键界面原型。设计仍围绕“创建房间到人机结算”的核心流程，教学和规则教练作为辅助入口，避免联机、账号与复杂扩展同时扩大工作量。

主要收获是明确了“玩家操作意图、规则状态和界面演出”三者的边界。一次点击、一次模型建议和一次动画结束都不能各自触发资源扣除，必须由统一命令入口校验后提交一次。模型可以给出策略和解释，但不能决定合法性；规则版本、超时预算、只读工具和降级机制共同约束其行为。数据库中的请求回执与事件序号也承担不同职责，前者防重复执行，后者保证演出顺序。

本次还发现了需求编号、玩家容量、首人到达后的结算和未接入联机入口等不一致之处，并在图、表及原型中统一。当前成果属于设计与原型验证，服务端权威状态、模型Agent、RAG和Harness尚未完成实现。下一步先落实统一命令和异常处理，再接入模型与检索；只有通过实际对局和故障测试后，才能确认其可靠性与性能达到验收目标。
